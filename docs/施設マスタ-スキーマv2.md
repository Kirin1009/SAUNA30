# 施設マスタ スキーマv2 —「最低限枠」定義書

2026.08.16版。**Kirin1009/Search-saunas（自前カタログ収集）と Kirin1009/SAUNA30（ととのい帳）の共通仕様**。競合分析（要件定義§11）の結論——「探す」を自前カタログで成立させるなら、サウナイキタイの施設ページ相当が器の最低ライン——を器として定義する。

**器と中身を分ける**のが本書の立場。スキーマは最初からフルで定義し、埋まるのは段階的（公式サイト由来→訪問時の観測）。空フィールドは恥ではない。器がないと観測を受け止められないことが問題。

---

## 1. 設計原則

1. **部屋は配列**。サ室・水風呂は1施設に複数ある前提（v1最大の変更点）
2. **全フィールドに出典が言えること**。値の出どころは `sources[]` と観測レコード（§5）で追える。サウナイキタイからの転記はしない（項目=事実の分類を揃えることは問題ない。値はクリーンルーム）
3. **null許容**。不明は null のまま持つ。捏造・推定での穴埋め禁止（実データ主義）
4. **後方互換**。v1（Search-saunas岐阜72件）・現行FAC/FRAMEからは機械変換で移行できる（§6）。読み込み側は全過去版を受理し続ける
5. **持たないと決めるもの**：混雑傾向（集合知が必要）、サ活・レビュー・サウナ飯（コミュニティ領域）、決済・クーポン（とゆとゆ領域）

## 3. フィールドの埋まり方（三層対応）

| 埋める主体 | 埋まるフィールド | 確度 |
|---|---|---|
| **公式カタログ層**（Search-saunasのクロール：公式サイト・紹介サイト） | name/address/geo(address精度)/type/fee/hours/holiday/tel/urls/facility の一部 | sources[]で追跡 |
| **観測層**（訪問者の現地実測。ととのい帳の入力） | saunas[]/waters[] の温度・部屋数・ロウリュ時刻・水深、rest、tattoo・pay等の実地確認、**geoのgps昇格** | 観測レコード（§5）で追跡 |
| 持たない | 混雑・レビュー・サ飯 | — |

**観測入力の上限ルール**（要件定義§8-6の答え）：訪問時に聞くのは**最大3項目・すべてスキップ可**。優先順＝①サ室の数と温度 ②水風呂の数と温度 ③「地図の位置、合ってた？」（geo検証）。それ以上の項目（設備・ロウリュ時刻等）は施設ページからの任意追記とし、押印フローには載せない（記録ファーストを殺さない）。

## 4. 検索が引ける条件（このスキーマで成立する絞り込み）

- 温度範囲：サ室◯°C以上（`saunas[].temp`）／水風呂◯°C以下（`waters[].temp`）
- 部屋数：サ室2つ以上・水風呂2つ以上（配列長）
- 型式：薪サウナ／スチーム／塩（`saunas[].style,heat`）
- 設備・ルール：深夜／予約制／タトゥーOK／駐車場／岩盤浴／サ飯（food）
- 従来チップ互換：シングル＝`min(waters[].temp)<10`、灼熱＝`max(saunas[].temp)>=100`
- 個人軸との横断（ととのい帳側）：上記×自分の採点・回数・行きたい

## 5. 観測レコード（ととのい帳側の持ち方）

観測は施設マスタを直接書き換えず、**パッチとして別持ち**する（公式層の凍結と両立）。

```jsonc
// totonoi:v1 に追加予定のフィールド（実装は栞・写真の後）
"obs": [
  { "fid": "g1", "at": "2026-08-16", "vid": "v123",   // どの訪問での観測か
    "patch": { "saunas": [{"temp": 92}], "waters": [{"temp": 16}, {"temp": 9}] },
    "geo_ok": true }                                    // 現在地とマスタ座標の一致確認
]
```

- 表示時は「マスタ＋自分の観測パッチ」を合成（自分の帳では観測が勝つ）。判子の勲章も合成後の値で描く＝**判子が観測で育つ**
- JSON交換（バックアップ/夫婦比較）に observations も含める＝β段階の「持ち寄り」の運搬単位

## 6. 移行対応表（既存→v2）

| 既存 | v2 |
|---|---|
| FRAME `m|w|u:[サ温,水温,外気浴,ロウリュ]` | `saunas:[{temp,bath}]`・`waters:[{temp,bath}]`・`rest.outdoor`・`louryu` に分解 |
| FAC/totonoi `smax` | `max(saunas[].temp)`（導出値として残してもよい） |
| FAC/totonoi `wmin` | `min(waters[].temp)` |
| `k`（施設タイプ） | `type` |
| `y`/`t`/`n` | `facility.reservation`/`stay_only`/`night` |
| `fee`（単一値） | `fee.min` |
| `hours`（文字列） | `hours.all`（曜日別が取れたら分解） |
| Search-saunas v1 `sauna_temp:"80-95"` | `saunas:[{temp:80,temp_max:95}]` |
| Search-saunas v1 `features[]` | 構造化できるものは各フィールドへ、残りは `features[]` |
| Search-saunas v1 `source_url` | `sources[]` |

移行は機械変換スクリプトで行い、**id・座標・イキタイ数の凍結アサート**を通してから書き出す（既存ルール踏襲）。

## 7. 運用メモ

- ととのい帳の埋め込みマスタは当面**現行スキーマのまま**でよい（v2化はスキーマ安定と観測層実装のタイミングで）。先に器を合意しておくことが本書の目的
- Search-saunasの次回収集（岐阜v2 or 他県v1）からこのスキーマで出力する
- v2.0.0の優先順位（栞・写真・誘導）はこの文書によって変わらない
