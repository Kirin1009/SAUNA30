# Part A. コンセプトシート

## A-1. プロダクトの一言

**「スタンプラリー」から「御朱印帳」へ。**
自分の帳を持ってサウナを歩き、行った先で一印もらう。帳は空欄なく押した順に育ち、あとから読み返せて、旅先では次の湯を教えてくれる。ラリーは表から消え、裏のオマケになる。

## A-2. 生い立ちと転換の背景

- 前身は2つの1ファイルPWA：**Sauna470s**（サウナイキタイの都道府県別イキタイ数TOP10×47県=470枠を固定し、GPSで踏破するコレクション帳）と**サ道場 東海**（東海5県TOP30=149湯を特性別お題で極める修行帳）
- 運用して得た本質的な気づき：**オーナー夫婦はTOP10ランキングで行き先を選んでいない。** 行く湯は生活と旅程で決まり、スタンプは後から「あ、枠だった」と押される。**ログが一次、ラリーは副産物**
- ラリー型の熱は構造的にスパイクする（近場の枠が尽きる1〜3ヶ月で「開く理由」が消える）。一方、記録の習慣（行った→残した→見返す）はサウナに行く限り毎週発火する
- そこで両アプリを「御朱印帳スタイル」の統合後継**ととのい帳**として作り直し中。既存2アプリはリリース後にととのい帳へ誘導予定（記録は無損失移行）

## A-3. 世界観の定義

| ラリー（旧） | 御朱印帳（新） |
|---|---|
| 主催者が枠を用意し、埋めに行く | 自分の帳を持ち歩き、行った先で一印もらう |
| 未達の枠が常に見える（負債感） | 空欄という概念がない。ページは押した順に増える |
| 全埋めで終わる | 一生綴じ続ける。満願は「後から気づく」 |
| どの施設も同じスタンプ | その施設でしか押せない一印（施設ごとの御朱印） |

- **御朱印帳との違いは「同じ湯に何度でも押せる」こと**。訪問のたびにページが増え、同じ施設の判子が重なる。回数そのものが誇り（常連判・◯回目）
- リワード設計の原則：**進捗バーを先に見せない。達成した瞬間に祝う**（追わされるのではなく、気づいたら成っている）

## A-4. ユーザーと利用文脈

- ユーザーは**オーナー夫婦2名のみ**（Shun・紗也乃、岐阜在住）。個人開発・個人利用
- スマホ（iPhone）のホーム画面に追加したPWAとして使う。表示基準は幅390px
- サウナは週1〜2回。地元の常連湯と、旅先での開拓が半々
- 将来構想として「誰でも自分のスタンプラリーを作れる基盤」への発展があるが、現段階のスコープ外

## A-5. 三つの目的（機能の柱）

1. **記録できる（コアループ）**：チェックイン（GPSまたは手動）→帳にその施設の御朱印が押される→採点・写真・支払・ひとことは任意で添える（スキップ可・後から追記可）
2. **探せる**：旅先で開くと近くの名サウナが出る（実データ569湯収録）。特性（シングル水風呂/深夜/銭湯/貸切/予約制/料金帯）と自分の過去（採点・行きたい・常連）で絞れる
3. **報われる（裏のオマケ）**：470枠踏破・県/地方/全国制覇・特性コンプ・カウント型（年間サ活/通算/常連/県またぎ）。リワードは帳に**栞が挟まる**形で現れる

## A-6. 画面構成（4タブ・承認済みビジュアルターゲットあり）

デザインは「完成イメージの絵を先に承認し、実装が逆算する」方式。2026.08.13に4画面の絵を承認済み。

| タブ | 役割 | 実装状況 |
|---|---|---|
| 帳（ホーム） | パスポートの査証ページ形式。判子が日付順に押し貯まり、最新だけ大判＋写真＋点数。再訪は重ね押し・幽霊判。判子タップで訪問詳細カード。最下部に「現在地で押印」固定 | α実装済み（素組み） |
| 探す | 手描き紙地図（実在地理・全国47都道府県投影）＋近い順リスト。ピン3態（訪問済=朱ベタ/未訪問=白抜き/行きたい=金縁）。絞りチップ＋地方→県セレクト | α実装済み |
| 棚 | 木の棚に集めた御朱印。未訪問は形の輪郭＋？で伏せ。回数の丸数字、10回で金の常連判。しつらえ小物（盆栽等）。進捗はここでだけ見える | α実装済み |
| 記録 | 訪問の時系列一覧・編集・手動記録の入口・設定・取り込み。実務の顔 | α実装済み（夫婦比較は未） |

## A-7. 意匠のアイデンティティ

- パレット：クリーム地 #FEF6E6 / 紙 #FBF6EA / こげ茶 #4A3B2E / 判子朱 #C8402F / 金 #C7973F。手描きテイスト
- **御朱印＝施設ごとの自動生成判子（facSeal）**。569湯すべて異なる：形=施設タイプ（丸=温浴・銭湯/角=貸切・カプセル/六角=宿/五角=アウトドア）、中央=頭文字、肩=市町村、勲章モチーフ=実データ（炎=サ室100°C/雪=シングル水風呂/月=深夜/鍵=予約制/小判=¥3,000以上）。かすれ（SVGフィルタ）・傾き（idハッシュ）・**押すまで伏せる**
- 絵入りの特注判は作らない（量産不能のため）。金の常連判のみ特別意匠
- 質感素材はデザイナーAI（チャッピー=Codex）が制作：和紙・和綴じ・紙地図・特性アイコン・木棚・小物を組み込み済み

## A-8. 採点思想（夫婦の議論で確定）

- **5軸（サウナ室/水風呂/外気浴・休憩/清潔・雰囲気/導線）×5点満点・0.1刻み＋特別加減点±2.5（理由必須）**。合計は100点換算表示。基準線：竜泉寺の湯≒82点
- 「整い」は採点に含めない（体調依存のため）。コスパは採点軸にしない（支払額は属性情報として記録）
- 旧Sauna470sの4軸×25点データは読み込み時に換算移行（各軸÷5・特別÷4・導線=2.5補完）

## A-9. システム構成

- **1ファイル主義**：`totonoi/index.html` 単体完結（約250KB）。依存ライブラリゼロ・ビルド工程なし。静的画像（質感素材19枚・約1.5MB）のみ別ファイル
- PWA：Service Workerがアプリ本体と素材をプリキャッシュ（圏外動作）。バージョンは`APP_VERSION`1箇所管理、SWキャッシュ名は自動追従
- データ：localStorage `totonoi:v1` に `{visits:[{id,fid,date,sc:{s:[5軸],x,why,v:2}|null,paid|null,note}],wants,ufacs,radius,imported}`。1訪問=1レコード・新しい順
- **統合施設マスタ569湯**を埋め込み（全国470枠＋東海99湯。名称・座標・イキタイ数・温度・料金・営業特性はサウナイキタイ由来の実データ。捏造禁止が絶対原則——座標が違うとGPS押印が壊れる）
- 地図：GeoJSON由来の投影座標SHAPES（約35KB）をSVG描画。沖縄インセット・最大64倍ズーム・ピンは最寄り数学判定＋重なり時候補シート
- 取り込み：同一オリジンの既存2アプリのlocalStorageを直読みしてワンタップ変換（冪等）
- GPS押印：半径100〜1000m設定、複数ヒット時は候補選択、半径外はその場で枠外登録
- 絶対ルール：**既存の記録・判子・写真を1件も失わない**／localStorageキー・バックアップ互換を壊さない／移行コードは消さない／外部ライブラリ・外部フォント・ビルド禁止

## A-10. 未実装（正式版v2.0.0までのロードマップ）

1. **写真**（撮る/選ぶ→圧縮→IndexedDB保存→帳のページにポラロイド風貼り込み。470sで実装済みの方式を移植）
2. **バックアップ書き出し/読み込み**（写真込みJSON）
3. **栞（達成リワード）**：県/地方/全国制覇・特性コンプ・カウント型の達成が「帳に金の栞が挟まる」形で現れる。進捗の事前表示はしない
4. **県鳥パズル・制覇証明書の移植**（470sの資産。県ごとの隠し絵が押印で開く遊びと、判子敷き詰めの証明書PNG）
5. **夫婦比較**（相手のバックアップJSONを読み込んで施設ごとに採点を並べる）
6. **既存2アプリからの誘導**（バナー→ワンタップ移行→以後はととのい帳を案内）
7. **帳のリッチ化**（進行中）：判子の存在感・重ね押しの乱れ・手書き風文字・帳の造作（ページの厚み/縁/めくれ）・写真貼り込みの演出を、承認絵の水準へ
8. localStorage `totonoi:v2` ストアへの移行（設計書あり。無損失移行パス）

# Part B. 分析指示

あなた（分析担当のClaude）への依頼です。Part Aのプロダクトを、**UX・UI・システムの3観点**から批判的に分析してください。

## B-1. 前提

- 分析対象は「構想を含む全体」です。実装済みαと未実装ロードマップ（A-10）を区別しつつ、**完成形の設計そのもの**を評価してください
- A-9の絶対ルール（データ不滅・実データ主義・1ファイル主義・外部依存禁止）は**オーナーの確定方針**です。これを壊す提案は禁止ではありませんが、「前提を変える提案」として明確に分離し、変える価値の根拠を添えてください
- ユーザーは夫婦2名の個人利用（A-4）。一般公開アプリの常識（オンボーディング・グロース・アカウント等）をそのまま当てはめず、**この2人が10年使い続けられるか**を軸にしてください
- お世辞は不要です。「よくできている」で終わる項目より、リスクと盲点の指摘に価値があります

## B-2. UX観点で分析すること

1. コアループ（行く→押す→添える→見返す）の摩擦。特に「採点シートへの自動遷移」はスキップ可とはいえ毎回出る——記録ファースト思想と噛み合っているか
2. 「進捗を先に見せない」リワード原則の妥当性と危うさ。達成に気づかない・忘れる問題への手当はどうあるべきか
3. 再訪（常連）体験。同じ湯に50回通ったとき、帳・棚・施設ページはどう見えるべきか。現設計で破綻しないか
4. 旅先での「探す」体験。現在地→候補→行く→押すの動線に欠けはないか
5. 夫婦2人利用の設計。比較ビュー（未実装）はどうあるべきか。「相手のバックアップJSONを読み込む」方式のUX上の限界
6. 10年スパンの継続性。記録が数千件になったときの「見返す」体験。年・季節・旅のまとまりで読み返す手段の欠如は問題か

## B-3. UI観点で分析すること

1. 4タブ（帳・探す・棚・記録）の情報設計。「帳と記録」「棚と探す」の役割分担は直感的か。迷いが生まれる場所はどこか
2. パスポート形式の帳面。判子が左右交互・傾き乱れで並ぶ表現の可読性と、タップターゲットとしての操作性の両立
3. 自動生成判子（facSeal）の識別性。569湯が「形＋頭文字＋勲章」で本当に見分けられるか。同名頭文字・同タイプの衝突時に何が起きるか
4. 幅390px基準の情報密度。地図（470ピン）・棚（47県グリッド）・帳（時系列無限）それぞれのスケール限界
5. 手描き世界観とアクセシビリティの緊張関係（判子朱の色覚多様性対応、かすれ文字の可読性、フォントサイズ）
6. 未実装の栞・写真・夫婦比較が入ったときのレイアウト圧迫。どこが崩れそうか

## B-4. システム観点で分析すること

1. 1ファイル約250KB＋データ埋め込みという構成のスケール限界。施設マスタを増やす（TOP10→TOP30、569→1500湯）とき何が最初に壊れるか
2. localStorageの容量・消失リスク（iOSのITP・容量制限・端末変更）。「記録を1件も失わない」原則に対してバックアップが手動任せで足りるか。自動保全の選択肢
3. `totonoi:v1`→`v2`ストア移行の設計リスク。移行コードを永続的に残す方針の保守コスト
4. 写真（IndexedDB・1280px圧縮）が数百枚になったときの容量・バックアップJSONの肥大
5. SVG地図・569判子のレンダリング性能。DOMノード量の観点で最も重い画面と、劣化したときの症状予測
6. 「誰でも自分のラリーを作れる基盤」への発展可能性。現アーキテクチャ（データ埋め込み・ビルドなし）から見て、何を今のうちに抽象化しておくべきか（ただし過剰設計への警告も歓迎）

3. **前提を変える提案**（あれば。A-9の絶対ルールに抵触するものはここに分離）
