# ととのい帳 — 第三者分析レポート

2026.08.14 / 分析担当: Claude(外部セッション想定・Part A準拠)
※公開αの実機表示も参照した(4タブ構成・取り込み導線・棚の伏せ判子・「現在地で押印」固定ボタンを確認)。

---

## 1. 総評

**本質的な強み**: 「ログが一次、ラリーは副産物」という転換が、机上の思想ではなく2つの前身アプリの**運用実感から帰納されている**こと。プロダクトの寿命を決めるのは熱のスパイクではなく毎週発火する習慣だという判断は正しく、御朱印帳メタファー(空欄がない・押した順に育つ・満願は後から気づく)はその判断を世界観レベルまで一貫させている。個人開発でここまで思想と意匠が噛み合っている例は稀。

**最大のリスク**: 「記録を1件も失わない」という絶対原則と、**localStorage単一コピー＋手動バックアップ任せ**という実装の間の乖離。10年スパンを謳うプロダクトで、データが常に「1台のiPhoneの中に1部だけ」存在する状態は、原則に対して構造的に無防備。端末変更・iOSアップデート事故・アイコン誤削除のどれか一つで帳が消える。v2.0.0の機能順序は、この乖離を埋めることを最優先に組み直すべき(→第5節)。

## 2. UX観点

### 強み

1. **事後祝福型リワード**は2人利用に正しく最適化されている。進捗バーの事前表示は「主催者に追わされる」構造を復活させるので、棚でだけ見える設計は原則として妥当。
2. **再訪の重ね押し・回数の丸数字・金の常連判**は、御朱印帳との差別化(何度でも押せる)を体験の誇りに変換できている。常連文化との整合が良い。
3. GPS押印失敗時の**枠外登録**が用意されている点。記録ファーストなら「マスタにない湯」で記録が止まらないことが生命線で、そこが塞がれていない。

### リスクと盲点

**R1. 採点シートへの自動遷移は、記録ファースト思想と正面から矛盾する。**
チェックインの瞬間はサウナ後で、疲れて・濡れて・連れがいる。5軸×0.1刻みの採点はその場でやる作業ではない。「スキップ可」は免罪符にならない——毎回出るシートは毎回スキップされ、スキップの摩擦だけが残る。さらに深刻なのは、「後から追記可」を支える導線が現設計に見当たらないこと。未採点の訪問はどこに溜まり、いつ思い出させてくれるのか。何もなければ「後から」は実際にはほぼ発生せず、採点データは新規開拓のテンションが高い日だけ残る偏ったログになる。

**R2. 「進捗を先に見せない」原則には、気づきの演出という対が必要。**
達成の瞬間を検知できるのはアプリだけなのに、栞が「静かに挟まる」だけなら、ユーザーは達成に気づかないまま何週間も過ごしうる。祝われない達成は、追わされる進捗バーより虚しい。また完全非表示は旅の楽しみを一部削る——「あと1県で東海制覇」を知っていたら旅程を1県ずらしたかもしれない、という種類の楽しみは、御朱印帳の世界観と実は矛盾しない(満願まであと幾つかは、帳を数えれば分かることだから)。原則は「押し付けない」であって「隠し通す」ではないはず。

**R3. 常連期の帳は、新規開拓期の設計のままでは単調化する。**
同じ湯に50回通うと、帳の直近ページは同じ判子の繰り返しになる。パスポート形式は「新しい査証が増える」時期に輝く表現で、常連期の主戦場は実質的に**施設ページ**へ移る。現設計で施設ページ(判子タップ→訪問詳細カード)がどこまで「その湯の歴史」を担えるかが未定義に見える。50回分の採点推移・写真・ひとことを一望できる「常連の間」がないと、最も熱心な使い方が最も報われない逆転が起きる。

**R4. 「見返す」手段の欠如は、10年アーカイブを死蔵させる。**
数千件の時系列無限スクロールは、記録装置としては成立しても読み物としては成立しない。ここは御朱印帳メタファー自身が答えを持っている——**帳は一冊で終わり、次の冊に移る**。年ごとに「冊」を綴じる(2026年の帳、2027年の帳…)、連続日程＋自宅から遠い訪問を「旅」として自動でまとまりにする、の2つがあるだけで、年末に一冊読み返す儀式が生まれる。これはB-2-6の懸念に対する、世界観を壊さない解。

**R5. 夫婦比較のJSON手動交換は、一番おいしいユースケースを取り逃す。**
「今この湯、相手は何点だった?」はサウナ上がりの休憩処で発生する会話で、その場でJSONを書き出して渡す人はいない。手動交換自体は月1の儀式として成立するが、設計を「比較タブ」ではなく**相手のスナップショットを端末に保持し、施設ページに相手の判子と点数を並置する**形にすれば、鮮度は落ちても会話には間に合う。スナップショットの取得日を明示すれば古さの誤解も防げる。

**R6. 「探す」は現在地起点に寄りすぎで、旅の前夜に弱い。**
旅先で開く動線は良いが、「行きたい(金縁)」を付ける主戦場は自宅でのプランニング。県セレクトからの探索で行きたい登録→旅先で金縁ピンが迎える、というループが意図通り回るか、自宅での探索体験(現在地から遠い県を眺める操作コスト)を一度検証すべき。

### 改善提案

| 提案 | 優先度 | コスト |
|---|---|---|
| 押印は押印で完結させ、採点は「後で添える」を正にする。未採点訪問は帳のページに**付箋**が覗く表現で示す(空欄ではなく「書きかけの栞」——世界観と両立する) | 高 | 小 |
| 栞達成時、**次回起動で帳がその栞のページで開く**一回性の演出を入れる。栞一覧は棚に置く | 高 | 小 |
| 施設ページを「常連の間」に拡張: 採点推移の小さな折れ線・全訪問の写真・ひとこと一覧 | 高 | 中 |
| 年ごとの「冊」区切り＋旅の自動グルーピング(連続日程×距離閾値) | 中 | 中 |
| 夫婦比較は独立ビューでなく施設ページへの並置。スナップショット取得日を表示 | 中 | 小 |
| 満願系の栞のみ「残りの数」を棚で数えられるようにする(バーではなく数) | 低 | 小 |

## 3. UI観点

### 強み

1. **facSealの生成ルールがデータ駆動**(形=タイプ、勲章=実データ)で、569湯すべてに手作業ゼロで固有性を与えつつ、判子を読めば施設特性が分かる情報デザインになっている。装飾と情報の一致は本作の白眉。
2. 「押すまで伏せる」棚は、コレクション欲の設計として的確。輪郭＋？は未達の負債感を与えずに好奇心だけを残す。
3. パレットと手描きテイストの一貫性。承認絵から逆算する開発方式は、個人開発の「動くが安っぽい」罠への有効な対策。

### リスクと盲点

**R1. 「帳と記録」の分担は、編集の瞬間に迷いを生む。**
閲覧の帳/実務の記録という分担は思想としては明快だが、「先週の点数を直したい」ときユーザーはどちらを開くか。帳の判子タップ→詳細→編集が完結しているなら記録タブは設定・取り込み・一覧の裏方でよいが、現α では手動記録の入口が記録タブにあり、発見性が低い。「現在地で押印」の失敗時フォールバックとしてだけでなく、押印ボタンの長押しや脇に手動押印の小さな入口があるべき。

**R2. facSealの識別性は、569湯では確実に衝突する。**
形4種×頭文字。「サ」「湯」「大」で始まる施設は全国に大量にあり、同一県内で(同形・同頭文字)のペアは必ず発生する。肩の市町村文字は390pxの棚グリッドサイズではほぼ読めない。ただしこれは致命傷ではない——識別の実務は棚の県別配置と施設名ラベルという**文脈**が担い、判子は同一性の証明ではなく愛着の対象だから。やるべきは、衝突を前提に**idハッシュで内枠・地紋を分岐**させて「並べたとき違って見える」ことの担保と、実データで同県内衝突ペアを数える検証。

**R3. 地図の初期状態が全国表示なら、それは装飾であって道具ではない。**
390pxに470ピンの全国図は眺める絵としては美しいが、探す道具としての初手は**現在地ズーム**であるべき。現在地取得前のワンテンポも含め、「旅先で開いて3秒で近くの湯が見える」を初期状態の定義にする。

**R4. かすれ・傾き・重ね押しと、タップターゲット/可読性の緊張。**
乱れは大判(最新ページ)では魅力、小サイズでは可読性の敵。判子単体に識別を負わせず、施設名テキストを常に併記する(現αはそうなっているように見える——維持すべき)。タップターゲットは判子の視覚サイズでなく44px以上のヒット領域を別途確保。重ね押し・幽霊判が密集したときのタップ解決は、地図で既にある「候補シート」方式を帳でも流用すればよい。

**R5. 色覚多様性: 朱ベタ/白抜き/金縁のピン3態は、金と朱が近接して見える型がある。**
幸い3態は塗り/抜き/縁という**形状差分**も持っているので方向は正しい。金縁は縁の太さか二重縁で差を強調し、色だけに依存しない現状を崩さないこと。判子朱#C8402Fとこげ茶#4A3B2Eのコントラスト比も、小さな肩文字では不足しうる。

**R6. 最新ページは要素の渋滞地帯になる。**
大判判子＋写真ポラロイド＋点数、そこに栞が加わると、390pxの1画面で最新エントリが縦に肥大する。栞は判子と同じレイヤーに置かず、**ページとページの間に挟まる独立要素**(帳の物理メタファー通り)にすれば、渋滞と世界観の両方が解ける。写真は最新のみ大判・過去はページ内サムネという現方針は正しい。

### 改善提案

| 提案 | 優先度 | コスト |
|---|---|---|
| 探すタブの初期状態を現在地ズームに(全国図はピンチアウトで到達) | 高 | 小 |
| facSeal衝突の実データ検証＋idハッシュによる内枠・地紋の分岐追加 | 中 | 小 |
| 手動押印の入口を帳の押印ボタン周りに追加 | 中 | 小 |
| 栞を「ページ間に挟まる」独立レイアウト要素として設計 | 中 | 中 |
| 判子のヒット領域44px確保・密集時の候補シート流用 | 中 | 小 |
| 金縁ピンの二重縁化など、色以外の差分強化 | 低 | 小 |

## 4. システム観点

### 強み

1. 依存ゼロ・ビルドなし・1ファイルは、**10年保守**という要件に対して実は最良に近い選択。npm生態系の腐敗と無縁で、2036年のブラウザでもほぼ確実に動く。
2. `APP_VERSION`一元管理＋SWキャッシュ名自動追従は、個人開発で最も事故りやすい「更新が届かない」問題への正しい手当。
3. 取り込みの冪等設計と換算移行の明文化(4軸→5軸)。移行を使い捨てにしない態度は原則と整合。

### リスクと盲点

**R1. データ保全: 現構成は「1件も失わない」を守れない。**(最重要)
ホーム画面追加PWAはSafariのITP 7日削除の対象外だが、それで安全なのではない。実際の喪失経路は (a) 端末変更——PWAのlocalStorage/IndexedDBはiCloudバックアップの対象として保証されない、(b) iOSメジャーアップデートでのストレージ消失事故(過去に実例が複数ある)、(c) ホーム画面アイコンの削除=データ削除、(d) ストレージ逼迫時のOSによる自動退避。手動バックアップ任せは「最後にいつ書き出したか」に喪失量が比例する構造で、原則に対して不十分。**外部依存禁止の枠内でできる自動保全**はある: ①`navigator.storage.persist()`の要求(退避対象から外れる確率を上げる。1行)、②起動時に前回バックアップからの経過日数と未保全件数を検知し、閾値超えで書き出しを促す(Web Share APIでiCloud Drive/ファイルAppへ直接渡せる)、③書き出しを「儀式」に格上げし、年綴じ(UX-R4)と結合して「一冊綴じ終えたら蔵に納める」体験にする。

**R2. スケール限界はファイルサイズではなくDOMが先に来る。**
569→1500湯でマスタは+150〜200KB程度、パースも問題ない。先に壊れるのは棚と地図のレンダリング(→R5)。つまり「1ファイル主義の限界」は当分来ない。逆に注意すべきはSWのプリキャッシュ設計: **キャッシュ名がAPP_VERSION追従だと、パッチ更新のたびに質感素材1.5MBを再取得する**。素材は変更頻度が低いので、アプリ本体(バージョン追従)と静的素材(安定名・内容変更時のみファイル名変更)の2キャッシュに分離すべき。

**R3. v1→v2移行より、バックアップJSONの版互換の方が本丸。**
移行コード永続保持は2人利用なら保守コストは軽微(移行完了を両端末で確認後、ガード付きで凍結すればよい)。真のリスクはバックアップファイル側: 5年前に書き出したJSONを新版が読めるか。**バックアップにschema versionを埋め、読み込み側が全過去版を受理する**ことを移行コードと同格の絶対ルールに昇格させるべき。バックアップこそが災害時の正本なのだから。

**R4. 写真をバックアップJSONに同梱する設計は、いずれ書き出し自体が失敗する。**
週2×10年≒1,000枚×圧縮後200〜400KB=300〜400MB。IndexedDB保存(Blob)は問題ないが、base64でJSONに内包すると+33%膨張の巨大文字列生成でメモリが尽きる。**データJSONと写真アーカイブを分離**すべき。外部ライブラリ禁止でも、無圧縮ZIP(store方式)はコンテナ仕様が単純で自前実装が数十行で書ける——写真はJPEG圧縮済みなので再圧縮不要、無圧縮で正しい。この分離はバックアップ形式の根幹なので、**写真機能の実装前に決めるべき設計判断**。

**R5. 最も重い画面は棚。SVGフィルタが主犯になる。**
569個のSVG判子×かすれフィルタ(feTurbulence系)は、GPU合成負荷が高く、iOSではスクロールのカクつき→メモリ警告→タブ再読み込みの順で劣化する。地図は470ピンでもピン自体が単純なら軽いが、ズーム時のフィルタ付き要素が混ざると同様。対策: **判子は初回生成時にcanvasでラスタライズしてdataURL/Blobをキャッシュ**し、一覧は画像として描画、フィルタ付きライブSVGは大判表示(最新ページ・詳細カード)だけに限定する。1500湯化の前提条件でもある。

**R6. 基盤化への布石は、2つだけで足りる。**
①施設マスタのスキーマを「サウナイキタイ由来」前提から独立させて文書化する(座標・特性・出典の必須/任意を定義)、②facSeal生成をマスタのフィールドのみから決定する純関数として保つ(現設計はほぼそうなっている)。この2つが保たれていれば、「誰でも自分のラリー」はマスタ差し替えで成立する。テーマ機構・プラグイン化・設定画面の一般化は、ユーザーが2人の現段階では過剰設計であり、着手すべきでない。

### 改善提案

| 提案 | 優先度 | コスト |
|---|---|---|
| `storage.persist()`要求＋未保全検知＋Web Share書き出し(自動保全の枠内最大) | 高 | 小 |
| バックアップ形式を「データJSON＋無圧縮ZIP写真」に分離、schema version埋め込み | 高 | 中 |
| SWキャッシュをアプリ/素材の2系統に分離 | 中 | 小 |
| 判子のラスタライズキャッシュ(棚・帳一覧は画像描画) | 中 | 中 |
| 施設マスタスキーマの文書化(基盤化の唯一の布石) | 低 | 小 |

## 5. 前提を変える提案

**P1. 「1ファイル主義」を「アプリ本体1ファイル主義」と再定義する。**
質感素材19枚とIndexedDB写真の時点で、厳密な1ファイル主義は既に破れている。守っている実質は「ロジックとデータ定義が1つのHTMLに集約され、ビルドなしで読める・直せる」ことであり、それは10年保守の核として正しい。定義を明文化して再定義すれば、写真アーカイブ分離(R4)や素材キャッシュ分離(R2)を原則違反の後ろめたさなしに進められる。**変える価値**: 原則が現実と食い違ったまま残ると、以後の設計判断のたびに原則の解釈で迷う。

**P2. 「外部依存禁止」に、データ保全のためだけの例外を検討する余地。**
枠内の自動保全(システムR1)を先に尽くすべきで、これは今すぐの提案ではない。ただし10年運用の途中で一度でもヒヤリとしたら、その時点で**2人利用に限った最小同期**(例: 各自のprivate Git リポジトリへのJSON push、あるいは自前の数十行のエンドポイント)を解禁する判断基準を、今のうちに決めておくことを勧める。「1件も失わない」と「外部依存ゼロ」が衝突したとき、どちらが上位原則かは明文化されていない——衝突前に序列を決めておくべき。私見では前者が上位。

## 6. v2.0.0までにやるべきトップ5

A-10の並べ替え＋分解。基準は「データ保全 > コアループの感情的完成 > 世界観の仕上げ > その他」。

1. **バックアップ書き出し/読み込み——ただし分離形式で**(A-10の2を昇格＋再設計)
   全機能の前提。写真同梱JSONで作ってしまうと後で作り直しになるため、写真実装より先に形式(データJSON＋ZIP写真、schema version)を確定する。`storage.persist()`と未保全検知もここに含める。
2. **写真**(A-10の1)
   コアループの感情的報酬の中心。470s実装の移植で済み、帳のページが「読み返したくなるもの」に変わる分水嶺。
3. **帳のリッチ化＋判子ラスタライズ**(A-10の7に性能対策を抱き合わせ)
   承認絵との乖離は毎日目に入るのでモチベーションに直結する。リッチ化(フィルタ・重ね押し表現)は描画負荷増加と同義なので、ラスタライズキャッシュと同時にやらないと棚が先に破綻する。
4. **栞——気づきの演出込みで**(A-10の3を拡張)
   「次回起動時に帳がその栞のページで開く」一回性の演出まで含めて1機能。挟まるだけの栞は作らない方がましなくらい、演出が本体。
5. **既存2アプリからの誘導・移行完了**(A-10の6)
   運用が3アプリに分裂している期間は、記録の正本が曖昧になり保全リスクそのもの。1〜4が揃い次第、速やかに一本化する。
