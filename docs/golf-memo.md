# ゴルフ場スタンプラリー（構想メモ・2026.08.07）

友人からのリクエストを受けた時点のメモ。**実装はしていない。** 着手するならロードマップ9（枠差し替え可能なスタンプラリー自作基盤）の最初の適用例になる。

## 元のリクエスト

- ゴルフ場のスタンプラリーが欲しい
- 軸は「**飯がうまい**」。コースの難易度や名門度ではなく、レストランが基準

サウナ版が「イキタイ数TOP10を枠に固定」でやっているのと同じ構造を、ゴルフ場の食事評価に置き換える発想。オーナー（Shun）の一存では決められない部分が多いので、まず出典と範囲を詰める。

## 追記（2026.08.07・友人に聞き直した）

友人が欲しいのは「飯がうまいコースを探して訪ねる」ではなく「**うまかったものを振り返る**」だった。事前のガイドではなく事後の記録。これで話が変わる。

**スタンプラリーには2つの側面がある。**

1. **ラリー**＝決められた枠を踏む。踏破のコレクション
2. **個人ログ**＝食べた記録を残す。ただし残すこと自体が目的ではない（下記）

### 価値の核＝個人的な飯ランキングにソートできること

ログは材料で、成果物は**自分が食べたものが自分の順位で並ぶこと**。「振り返る」の実体はこれ。ここが分かっていないと、ただの記録アプリを作って外す。

帰結：

- **外部ランキングは要らない**。楽天GORA等を枠の基準にすると、主役（自分の順位）を外部の順位が食う
- **ソートが成立する条件は全件が同じ尺度で採点されていること**。採点が任意だと穴あきになりソートが壊れる。**入力は軽く、必須は1つの点数だけ**に絞るべき。サウナ版の4軸×25点＋特別加減点はここでは重すぎる（サウナは施設が主語で件数が少ないから成立している）
- 絶対点で付けると後半インフレして順位が信用できなくなる。**新しい一食を既存の数件と比べて挿し込む対戦式**なら、母数が増えるほど順位が正確になる。どちらを採るかは要検討
- ラリー側の枠は、ランキングの母集団を作るための「行った証」に格下げされるかもしれない

サウナ版のCLAUDE.mdにある「枠と台帳は別の欲求」と同じ構造だが、**層の切り分け方が違う**。サウナ版は両層とも主語が場所（枠＝TOP10の施設／台帳＝それ以外の施設）。ゴルフ版は枠＝コース、ログ＝**そこで食べた一食**で、層をまたぐと主語が変わる。飯はラリー側ではなくログ側の主題。

## 枠の出典（候補）

上の追記により、**飯ランキングを枠の基準にする必然性は薄れた**。楽天GORA等のレストラン評価が県別に取り出せるかどうかは、もう前提条件ではない。枠は「行けるコース」で素直に組み（何のランキングを版にするかは要相談）、飯はログ側に持たせるほうが友人の欲求に合う。

飯を枠の基準にする案を残す場合、以下は未確認のまま：

- レストラン単体の評価が県別ランキングとして取り出せるか（総合評価しか並ばない可能性がある）
- 取得の可否と利用規約。サウナイキタイと同様に bot 対策がある想定
- この環境のネットワーク許可（現在許可済みなのは sauna-ikitai.com のみ）

どの案でも、出典が確定するまで枠データは作らない。**捏造データは入れない**（実データ主義。座標が違うとGPSスタンプが壊れるのはサウナ版と同じ）。

## 決めていないこと

- **範囲**：全国47都道府県 × TOP10 で 470枠にするか、まず東海だけにするか。ゴルフ場は移動コストがサウナと桁違いなので、470枠だと一生かかる。友人が一人で埋められる密度に落とすべきかもしれない
- **採点軸**：サウナ版の4軸×25点＋特別加減点±10に相当するものを何にするか。飯が主題なら「料理の味／ボリューム／名物の有無／コースそのもの」あたりが候補だが、これは友人と決める話（サウナ版の軸を妻と詰めたのと同じ手順を踏む）
- **判子の字**：サウナ版は「岐1」＝県一文字＋順位、台帳は「湯」。ゴルフ版の台帳相当は「飯」か「打」か
- **GPS判定**：ゴルフ場は敷地が広い（クラブハウスからコース端まで1km超あり得る）。サウナ版の100-1000m設定をそのまま使うと、隣接コースを誤爆する可能性がある。**クラブハウスの座標を基準にして半径を絞る**のが素直
- **隠し絵パズル相当**を作るかどうか（47枚の生成イラストは2026.08.06に作り切ったが、同じ物量をもう一度やるかは別問題）

### ログ側（振り返り）で決めていないこと

- **記録の単位**：サウナ版は「施設1件に対し訪問が複数」。ゴルフ版は「コース1件に対しラウンドが複数、1ラウンドに一食」が素直。ただし振り返りたいのが料理そのものなら、**うまかった順に並べる単位は料理か、コースか**。同じコースで別の日に別のものを食べた場合にどう見せるか（サウナ版の「施設スコア＝最新の採点付き訪問」に相当するルールが要る）
- **一食に持たせるフィールド**：料理名／写真／★／一言、あたり。サウナ版の写真まわり（1280px・JPEG圧縮・IndexedDB）はそのまま流用できる
- 採点軸をコースに付けるのか一食に付けるのか。飯が主題なら**一食側**に付くはずで、これはサウナ版（施設に付く）と構造が違う

## 実装形態

**別リポジトリを立てる**方針（2026.08.07決定）。このリポジトリには作らない。

理由：index.html 単体完結で、FRAME / PREF / SHAPES がサウナ前提（浴室別の分母 `bath`、サウナ室温度・水風呂温度のフィールド、県鳥パズル）。同居させると既存ユーザー（本人と妻）のデータ構造に触ることになる。既存の `sauna30:v2` / IndexedDB `sauna30` には手を入れない。

このリポジトリ側でやることは無い。**このメモは着想の記録**であって、続きは新リポジトリで書く。
